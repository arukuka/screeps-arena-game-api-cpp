## 定数の扱い

`include/arena/constants.h` は **推測しない**。

- typings に値があるもの → そのまま転記
- typings に型しか無いが実機で測ったもの (`BODYPART_COST`,
  `rangedMassAttackRate`, `SPAWN_ENERGY_REGEN`, 疲労まわり) →
  **測定方法をコメントに残して**定義
- 値も測定も無いもの (`OBSTACLE_OBJECT_TYPES`, `RESOURCES_ALL`,
  `CONSTRUCTION_COST`) → **定義しない**。
  `arena::obstacleObjectTypes()` などで実機から読む

`getDirection()` も同じ理由で C++ 実装していない。Chebyshev 距離
(`getRange`) は確実なので C++ で計算するが、任意の delta を 8 方向へ
丸める規則はゲーム側の仕様であり、推測すると静かに間違った移動をする。

実測値の出所は arukuka/screeps-arena-bot `src/constants.ts`。

## 配布単位

### なぜ npm で C++ ごと配るのか

`src/bridge.cc` が呼ぶ名前と `host.mjs` のキーは一致していなければならない。
C++ と JS を別経路 (FetchContent と npm など) で取得できるようにすると、
**バージョンがずれた組み合わせが成立してしまい、誰も気づけない。**
1 パッケージ 1 バージョンにすることで、この破綻を構造的に防いでいる。

## オブジェクト表現

ゲームオブジェクトは `emscripten::val` ハンドル**と** tick ごとの
スナップショットへの添字を持つ。読み取りはスナップショットから、
行動はハンドル経由。シグネチャはどちらでも同一なので、ボットのコードは
自分がどちらで動いているか知らない。

### なぜ片方に寄せないのか

ハンドルだけではプロパティ 1 つにつき境界越え 1 回かかる。
純スナップショットにすると行動もバッチ化することになり、
バッチ化は結果コードを諦めることを意味する。
`if (creep.harvest(s) == ERR_NOT_IN_RANGE)` は Screeps のボットが必ず書く形で、
「答えは次の tick」の行動では成立しない。

計測が言ったのは、その取引は不要だということ。読み取りは
オブジェクト数 x フィールド数 x pass 数 だけ起きるが、行動は creep あたり
1〜2 回しかない。読み取りを安くすればほぼ全ての利得が得られ、
表現力は何も失わない。

### 列単位・初回アクセス時に読み込む

スナップショットは**列単位で、初回アクセス時に**埋まる。どれか 1 体の creep に
`hits` を聞くと、そのスライス全体の `hits` が 1 回の境界越えで埋まり、
以降の読み取りは単なるメモリアクセスになる。

これは最初の設計ではない。最初の設計は間違っていた。18 フィールドの固定
レコードを先読みする方式は、実機で creep 28 体・tick あたり 104us かかった。
生ハンドル 1 pass の約 2 倍であり、世界を 1 回しか読まないボットは以前より
遅くなっていた。Arena のゲームオブジェクトのプロパティは JavaScript から
読んでも約 150ns かかるので、コストは読むフィールド数にほぼ線形で、
そのほとんどは誰も聞いていないフィールドだった。

列単位にすれば、ボットは読んだフィールドの分だけを、何回読んでも 1 回だけ払う。

### 何がスナップショットに載るか

数値フィールドは `arena::detail::Field` に列挙され、`js/host.mjs` の
`snapshotField` が各フィールドの読み方を知っている。文字列・配列・入れ子の
オブジェクトはハンドルのまま。固定幅の int32 レコードでは運べない。

`getObjectById()` と `getObjects()` が返すオブジェクトはレコードを持たず、
ハンドル経由で読む。正しいがフィールドごとに遅いので、
多くのフィールドを読むなら `getObjectsByPrototype()` を使うこと。

レイアウトは言語をまたいで二重に持っているため、
`tests/snapshot.test.mjs` がヘッダの enum を解析して食い違いを検出し、
`tests/objects.test.mjs` が WASM 内で全フィールドを両経路から読んで
一致を検証する。速くて微妙に間違っているスナップショットはクラッシュしない。
ボットが間違った数値で判断するだけである。

Arena は tick あたりの実時間 CPU (`arenaInfo.cpuTimeLimit`) で課金されるため、
creep 50 体を本格的に回す段階で CPU が問題になったら、tick 頭に状態を
**1 回だけ** WASM のリニアメモリへ書き出すスナップショット方式への移行を
検討すること。

`sim/world.mjs` の `apiCalls` カウンタと `arena::testing::getTicksCallCount()` は
境界越えの回数を数える道具で、1 回のコストは `bench/` で測ってある。
Pain and Gain での数値は、ハンドル経由のプロパティ読み取りが約 0.5 マイクロ秒、
同じフィールドが WASM メモリにあれば 0.24 ナノ秒、tick 予算は 100ms。
このうち約 70% は境界越えそのもので、だからこそ世界全体を 1 回の境界越えで
写すバルクスナップショットは、0.5 pass 未満で元が取れる。

移行するとオブジェクトのプロパティは struct のフィールドになり、
行動の戻り値をその tick で得られなくなる (`ERR_NOT_IN_RANGE` を見て分岐する
書き方ができなくなる) ため、API の形が変わる。安くはない。
