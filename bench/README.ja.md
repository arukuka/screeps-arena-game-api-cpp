# JS 境界のコスト

**日本語** | [English](README.md)

オブジェクトモデルは `emscripten::val` ハンドルを渡すので、プロパティ 1 つ
読むたびに JavaScript へ往復する。対する選択肢は、tick の頭で世界を WASM
メモリへ 1 回だけ書き出し、以降は plain struct として読むスナップショット方式。
どちらが良いかは両者の比で決まるが、README に正直に書いてあったとおり
**誰も測っていなかった**。

```sh
npm run bench                # creep 50 体
npm run bench -- --creeps 5
```

## 実機での測定結果

Pain and Gain、creep 28 体。1 pass = 28 体 x 5 フィールド = 140 回の読み取り。

```
benchmark                       iters     total us        ns/op
-------------------------- ---------- ------------ ------------
getCpuTime()                     1000       1724.4       1724.4   (1 call)
C++ arithmetic                 200000        266.6          1.3   (1 add)
getTicks()                       1000        311.7        311.7   (1 call)
creep.hits()                     2000       4689.8       2344.9   (1 property)
scan creeps: val handles           20       5118.9     255945.2   (1 pass)
scan creeps: C++ snapshot        2000        127.0         63.5   (1 pass)
getObjectsByPrototype              50        235.6       4712.9   (1 call)
```

読み取り 1 回あたり:

| | ns / 回 | C++ の加算比 |
|---|---|---|
| val ハンドル経由のプロパティ | 約 1,830 | 約 1,400 倍 |
| C++ スナップショットのフィールド | 約 0.45 | 約 0.35 倍 |

**ハンドル経由のプロパティ読み取りは約 1.8 マイクロ秒。**
tick 予算は 100ms なので、**tick あたり約 55,000 回**のプロパティ読み取りができる。

`getObjectsByPrototype()` は creep 28 体で約 4.7 マイクロ秒（1 オブジェクト
約 170ns）。フィールドを 1 つも読む前に、プロトタイプごとに毎 tick 払う。

### 面白いのはここ

同じベンチを Node（`npm run bench`）と実機で比べる:

| | Node | 実機 | 比 |
|---|---|---|---|
| ハンドル経由のプロパティ | 約 120〜300ns | 約 1,830ns | **約 10 倍悪化** |
| スナップショットのフィールド | 約 0.45ns | 約 0.45ns | 同じ |
| `getObjectsByPrototype` の 1 オブジェクト | 約 160ns | 約 170ns | 同じ |

**一括の配列取得は isolated-vm でも悪化しておらず、WASM ローカルのメモリも同じ。
悪化したのは個々の往復だけ。** Arena のサンドボックスが課すコストは
**1 回の境界越えごと**にかかる。したがって対策は「仕事を減らす」ではなく
「境界越えの回数を減らす」。

### 素朴なスナップショットは藁人形だった

上の表の `take snapshot` は、C++ から各ハンドルを読んでスナップショットを
作っている。フィールドごとに境界を越えるので、ハンドル走査と同じコストが
かかって当然である。**スナップショット方式とはそう作るものではない。**

本物は、WASM メモリの typed view を JavaScript へ渡してそちらに埋めさせる。
**フィールド数に関係なく、世界全体で境界越えは 1 回。**
`bulk snapshot (1 crossing)` がそれを測っている。Node、creep 50 体:

| | ns / pass | ハンドル 1 pass 比 |
|---|---|---|
| ハンドル走査 | 約 93,000 | 1 倍 |
| 素朴なスナップショット (C++ が読む) | 約 72,000 | 0.8 倍 |
| **バルクスナップショット (JS が埋める)** | **約 9,000** | **0.10 倍** |

損益分岐は「世界を 1 回なめる」ではなく、**その 10 分の 1 あたり**。
世界を 1 回読むだけのボットでも、ハンドル経由はスナップショットの 10 倍払っている。

これは実機の測定とも整合する。一括の `getObjectsByPrototype()` は
isolated-vm でも悪化せず、個々のプロパティ読み取りだけが 10 倍悪化した。
サンドボックスは境界越えの回数に課金し、バルクスナップショットはそれを
ちょうど 1 回で済ませる。

### この数値の注意点

上の測定は反復 20 回・暖機 3 回の旧版で取ったもので、それが露呈している。
スナップショットの作成が、**同一の読み取りを行う**ハンドル走査より 3.5 倍速く
見えていた。ありえない。最初の pass 単位ベンチが V8 の最適化コストを
肩代わりしていた。

現在の `measure()` は `iterations / 2 + 8` 回暖機し、pass 単位のベンチは
20 回でなく 60 回回す。この変更後、ローカルでは両者が 1% 以内で一致する。
**したがって上の絶対値はハンドルコストの上限とみなすべきで、
きれいな数値が要るなら取り直すこと。**

その他:

- **`getCpuTime()` 自体が境界越え**で、実機で約 1.7 マイクロ秒。
  各計測が 2 回呼ぶが、上の合計に対しては誤差。ただし自分のボットを
  計測するときは効いてくる。
- **`cpuTimeLimit` の単位はナノ秒。** typings に記載が無い。生の値が 1e8 で、
  ナノ秒なら 100ms、他の解釈ではいずれも非現実的。初回 tick は 1e9（1 秒）。
- **シミュレータは[近似](../sim/FIDELITY.ja.md)。** ローカルの数値が語るのは
  境界のことであって、試合のことではない。

## 結論

損益分岐は **tick あたり世界を 1 回なめる**あたりにある。スナップショットを
取るコストがハンドル経由 1 pass とほぼ同じで、2 回目以降は実質タダになる。

- creep を tick に **1 回** しか見ないボットは、スナップショットにしても得しない。
  ハンドルのほうが単純で、コストは同じ。
- 世界を**繰り返し**見るボット — 標的の評価、複数プランの比較、探索 — は
  毎回フルの境界コストを払う。スナップショットなら 2 回目以降が単なる
  メモリ読み取りになる。

現状ハンドルを採っているのは、JS API と同じに読め、行動の結果コードを
そのまま返せるから。実機のプロファイルで境界が tick 予算を食っていると
分かったら、スナップショットへ移る際の API の変化は
[docs/DESIGN.ja.md](../docs/DESIGN.ja.md) にある。
