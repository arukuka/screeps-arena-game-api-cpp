# JS 境界のコスト

**日本語** | [English](README.md)

オブジェクトモデルは `emscripten::val` ハンドルを渡すので、プロパティ 1 つ
読むたびに JavaScript へ往復する。対する選択肢は、tick の頭で世界を WASM
メモリへ 1 回だけ書き出し、以降は plain struct として読むスナップショット方式。
どちらが良いかは両者の比で決まるが、README に正直に書いてあったとおり
**誰も測っていなかった**。

```sh
npm run bench                # creep 50 体
npm run bench -- --creeps 5
```

## 実機での測定結果

Pain and Gain、creep 28 体。1 pass = 28 体 x 5 フィールド = 140 回の読み取り。

```

-------------------------- ---------- ------------ ------------
getCpuTime()                     1000       1268.8       1268.8   (1 call)
C++ arithmetic                 200000        266.6          1.3   (1 add)
getTicks()                       1000        877.5        877.5   (1 call)
creep.hits()                     2000       4458.1       2229.0   (1 property)
scan creeps: val handles           60       4183.1      69717.8   (1 pass)
take snapshot                      60       4534.0      75566.5   (1 pass)
scan creeps: C++ snapshot        2000         67.3         33.7   (1 pass)
bulk snapshot (1 crossing)        200       5409.5      27047.4   (1 pass)
scan creeps: bulk buffer         2000        115.6         57.8   (1 pass)
getObjectsByPrototype             200       1125.8       5628.8   (1 call)

wasm memory: 約 1 MB / 16 MB
```

読み取り 1 回あたり:

| | ns / 回 |
|---|---|
| val ハンドル経由のプロパティ | 約 500 |
| WASM メモリのフィールド | 約 0.24 |

**ハンドル経由のプロパティ読み取りは約 0.5 マイクロ秒。**
100ms の tick 予算に対し **tick あたり約 20 万回**。暖機不足だった初回の
測定が示唆したより、はるかに余裕がある。

### 0.5 マイクロ秒の内訳

バルクスナップショットは creep を列挙してから同じ 140 フィールドを読むが、
JavaScript 側で読む。列挙分を引くと、境界を一切越えない場合の
プロパティ読み取りコストが出る。

| | ns / 回 |
|---|---|
| Arena オブジェクトのプロパティを JS から読む | 約 150 |
| その上に乗る WASM 境界のコスト | 約 350 |
| **合計（ハンドル経由）** | **約 500** |

つまり**ハンドル読み取りの約 70% が境界越え**で、30% は Arena のオブジェクトを
読むこと自体のコスト。スナップショットは前者を消し、後者は 1 回だけ払う。

実機でバルクスナップショットが素朴版の 3 倍しか安くない（Node では 8 倍）のも
これで説明がつく。Arena のゲームオブジェクトは読むこと自体が高く、
そこはバッチ化しても消えない。

### 未解決の食い違い

`creep.hits()` を単独で測ると約 2,230ns、同じ種類の読み取りを走査の中で
測ると約 500ns になる。1 つのオブジェクトの 1 つのプロパティを繰り返し読む
ほうが**速い**はずで、4 倍遅い説明がまだ付いていない。

1 回あたりの数値は約 500〜2,200ns の幅とみなすこと。上では走査側の数値を
採っている。ボットが実際にやるのは走査だから。

## ヒープ 16MB で足りるのか

ベンチが実使用量を報告する。実機で普通に動くボットは **16MB のうち約 1MB**、
しかもその大半は 1MB のスタックである。

増やすなら `INITIAL_MEMORY` を上げること。**`ALLOW_MEMORY_GROWTH` は
有効にしないこと。** 拡張は WASM の `ArrayBuffer` を detach して差し替えるため、
それを見ている JS 側のビュー — `snapshotCreeps` が書き込むビューを含む — が
すべて無効になり、**書き込みがエラーも出さずに消える**。
根拠は `cmake/ArenaBot.cmake` のフラグの隣に書いてある。

## 結論

損益分岐は **tick あたり世界を 1 回なめる**あたりにある。スナップショットを
取るコストがハンドル経由 1 pass とほぼ同じで、2 回目以降は実質タダになる。

- creep を tick に **1 回** しか見ないボットは、スナップショットにしても得しない。
  ハンドルのほうが単純で、コストは同じ。
- 世界を**繰り返し**見るボット — 標的の評価、複数プランの比較、探索 — は
  毎回フルの境界コストを払う。スナップショットなら 2 回目以降が単なる
  メモリ読み取りになる。

現状ハンドルを採っているのは、JS API と同じに読め、行動の結果コードを
そのまま返せるから。実機のプロファイルで境界が tick 予算を食っていると
分かったら、スナップショットへ移る際の API の変化は
[docs/DESIGN.ja.md](../docs/DESIGN.ja.md) にある。
