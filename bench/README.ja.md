# JS 境界のコスト

**日本語** | [English](README.md)

オブジェクトモデルは `emscripten::val` ハンドルを渡すので、プロパティ 1 つ
読むたびに JavaScript へ往復する。対する選択肢は、tick の頭で世界を WASM
メモリへ 1 回だけ書き出し、以降は plain struct として読むスナップショット方式。
どちらが良いかは両者の比で決まるが、README に正直に書いてあったとおり
**誰も測っていなかった**。

```sh
npm run bench                # creep 50 体
npm run bench -- --creeps 5
```

## 出力の読み方

```
benchmark                       iters     total us        ns/op
-------------------------- ---------- ------------ ------------
C++ arithmetic                 200000        168.0          0.8   (1 add)
getTicks()                       1000        243.9        243.9   (1 call)
creep.hits()                     2000        888.7        444.3   (1 property)
scan creeps: val handles           20        614.9      30745.8   (1 pass)
take snapshot                      20        571.6      28581.3   (1 pass)
scan creeps: C++ snapshot        2000        222.2        111.1   (1 pass)
getObjectsByPrototype              50        390.5       7810.0   (1 call)
```

1 pass = creep 50 体 x 5 フィールド = 250 回の読み取り。効くのは 3 行:

| | ns / pass | ns / フィールド |
|---|---|---|
| val ハンドル経由 | 約 30,000 | 約 120 |
| C++ スナップショット | 約 110 | 約 0.4 |

**プロパティ 1 つの読み取りは、同じデータが WASM メモリにある場合の約 300 倍**、
C++ の加算 1 回の約 150 倍かかる。設計判断はこの数値で決まる。

`getObjectsByPrototype()` は creep 50 体で約 8 マイクロ秒（1 オブジェクトあたり
約 160ns）。プロトタイプごとに毎 tick 支払い、そのうえで読むフィールドの分が乗る。

## この数値が言っていないこと

- **これは Node の数値である。** Arena はユーザーコードを isolated-vm で動かす。
  同じ V8 が同じ仕事をするので**比**は移ると期待できるが、絶対値は移らない。
- **ここの `getCpuTime()` はシミュレータの実装**で、呼び出しを数えて
  `performance.now()` を読む。その自身のコスト（約 1 マイクロ秒）は実機とは
  無関係。各計測が使う 2 回の呼び出しが合計に対して無視できることを示すために
  表に載せているだけ。
- **実際の試合について何も主張していない。** シミュレータは
  [近似](../sim/FIDELITY.ja.md)である。

判断に使える数値が要るならデプロイする:

```sh
ARENA_DIR=~/ScreepsArena/season4-pain_and_gain npm run bench:deploy
```

1 tick につき 1 つのベンチを走らせ（Arena は tick あたりの実時間 CPU で課金され、
全部を 1 tick でやろうとすると打ち切られる）、tick 9 で表を出す。
反復回数は 50ms 予算に十分収まるようにしてあるが、打ち切られるようなら
`bench/bench.cc` で下げること。

## 結論

損益分岐は **tick あたり世界を 1 回なめる**あたりにある。スナップショットを
取るコストがハンドル経由 1 pass とほぼ同じで、2 回目以降は実質タダになる。

- creep を tick に **1 回** しか見ないボットは、スナップショットにしても得しない。
  ハンドルのほうが単純で、コストは同じ。
- 世界を**繰り返し**見るボット — 標的の評価、複数プランの比較、探索 — は
  毎回フルの境界コストを払う。スナップショットなら 2 回目以降が単なる
  メモリ読み取りになる。

現状ハンドルを採っているのは、JS API と同じに読め、行動の結果コードを
そのまま返せるから。実機のプロファイルで境界が tick 予算を食っていると
分かったら、スナップショットへ移る際の API の変化は
[docs/DESIGN.ja.md](../docs/DESIGN.ja.md) にある。
